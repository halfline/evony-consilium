# Application architecture

Evony Consilium is a static application built from native JavaScript modules. `web/` is the deployable source tree. `scripts/build.js` copies maintained source and branding to `dist/`, generates policy pages, and runs asset acquisition and extraction through `scripts/assets.js`. Downloaded bundles are cached under `.asset-cache/`; generated game resources are ignored by Git. Extraction runs during the build, separately from the browser application. `npm run assets` prepares those resources for local development. The deployed application requires no bundler, framework, or backend.

## Dependency boundaries

| Directory                  | Responsibility                                                                                                                                                                       |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `web/src/domain/`          | Serializable team data, validation, player commands, map layouts, placement/collision rules, formation ranking, castle appearances, and parsing. No DOM, storage, or network access. |
| `web/src/application/`     | The active team document, atomic edits, bounded Undo history, march drafts, placement selection, subscriptions, and derived asset lookup. Depends only on domain modules.            |
| `web/src/ui/`              | Screens, forms, selection, gestures, dialogs, and presentation of errors. Composes application state and external services.                                                          |
| `web/src/rendering/`       | Canvas drawing and coordinate conversion using domain rules. No screen-controller dependencies.                                                                                      |
| `web/src/services/`        | Resource loading, folder/file access orchestration, synchronization, remote revisions, and save/reload coordination.                                                                 |
| `web/src/services/google/` | OAuth session lifetime, Drive transport, Picker authorization, and shared scope definitions.                                                                                         |
| `web/src/persistence/`     | IndexedDB drafts, serialized writes, account-scoped remembered teams, and draft recovery decisions.                                                                                  |
| `web/src/io/`              | Browser file and image reading. No application-state mutations.                                                                                                                      |

`web/app.js` loads resources and supplies the browser-workspace factory. `ui/planner.js` creates the store, renderer, and screen controllers and connects their callbacks. `application/placement-selection.js` owns primary/group selection and pending placement; `ui/placement-view.js` presents placement guidance and previews. `services/team-workspace.js` owns account and shared-document lifetime, authorization, creation, draft recovery, and remembered teams. `services/browser-workspace.js` constructs browser transports and persistence adapters.

Runtime modules have no import-time DOM or network effects. Tests enforce dependency direction for every runtime layer, resolvable imports, and the absence of module cycles. UI controllers cannot import Google transport clients directly. Screen controllers receive explicit DOM roots through `ui/dom.js`; only the planner composition root performs global shell lookup. The view-contract checks verify unique shell IDs and declared literal controller lookups. Prefer a direct import from the module that owns a capability over a general-purpose utility barrel.

## Team state and editing

`application/team-store.js` owns the authoritative in-memory plan and Undo history. Controllers read the current plan through `getPlan()`. Stored documents are recursively frozen to prevent edits outside a transaction. All edits use `commit(nextPlan)` or `mutate(callback)`; neither path mutates the previous snapshot. The store refreshes derived castle appearances and asset lookup, synchronizes the active map layout, and emits an event. Identical edits do not create history entries. Undo retains up to 20 immutable snapshots without cloning unchanged history.

`replace()` validates externally loaded documents and resets history. `openMap()` changes navigation without creating an edit or an Undo entry. Store events drive local draft scheduling and screen rendering. Draft scheduling precedes the full screen render.

`domain/validation.js` is the external-document boundary. Small field constraints live in `domain/constraints.js`; player-profile validation lives in `domain/players.js`. Older single-map documents and team-wide alliance tags normalize here. Unknown player fields are retained so subsequent profile features do not lose data during map editing or older-client use.

`domain/entities.js` centralizes construction and entity caps; `domain/appearance-commands.js` shares footprint checks for player/building appearance changes. `domain/players.js` provides profile edits and player removal. The profile edit command accepts an explicit field list and cannot write map coordinates or locks. Removing a player also removes their map placement references. `domain/layout.js` owns the layout field list and capture/apply operations; `domain/map-plans.js` owns named-map lifecycle and shared-content fingerprints. Fingerprints exclude navigation state and normalize JSON object key order, so switching maps or reformatting JSON does not create a false edit.

## Screens and controllers

- `ui/team-entry.js` presents sign-in and team selection/creation through a workspace service. `team-tabs.js`, `team-list.js`, `account-menu.js`, and `entry-progress.js` own their respective controls. Showing login clears the account context and invalidates pending navigation. Out-of-order downloads cannot replace the current team.
- `ui/team-screen.js` owns team settings; `ui/team-dashboard.js` presents player, subcity, and map counts and navigation. Team settings include shared name, logo, Discord link, and navigation through player/map counts. `logo-picker.js` constructs one reusable logo control and handles image upload and removal for creation and editing. Discord uses the bundled official icon and opens the saved URL without widget configuration or background Discord requests.
- `ui/player-workflow.js` coordinates player creation, profile navigation, avatar browsing, and the last-used alliance tag. `ui/players-screen.js` owns the player grid and search. `ui/player-screen.js` owns the dedicated profile page. `ui/add-player-dialog.js` holds an uncommitted draft until submission, defaulting to level 42 and Japan. Avatar and castle browsers have independent catalogs and controllers. Avatar and subcity-owner pickers reuse `ui/searchable-picker.js` for search, selection, and dialog lifetime, and `ui/portrait.js` for portrait content; their catalogs, filters, and permissions stay in their feature controllers.
- `ui/maps-screen.js` owns map tiles and the Add Map dialog. Empty map lists open the dialog directly. `ui/formation-list.js` owns placement rows, `ui/formation-controls.js` owns rally/layout/building controls, and `ui/map-setup.js` owns grid/background/custom-resource controls.
- `ui/placement-inspector.js` edits map coordinates, footprint, locks, and building appearance. It has its own permanent DOM host and never reads profile-form fields. The player page and map inspector are separate forms.
- `ui/map-interaction.js` owns pointer and keyboard gestures; `domain/placement-commands.js` owns atomic group moves and removals. Leaving a screen, changing maps, loading another team, or undoing cancels an in-progress gesture. Dropping keeps off-map removes placements while preserving profiles; deleting selected buildings removes those buildings. Fixed landmarks are not editable entities.
- `ui/tile-actions.js` shares hover/long-press removal behavior across grids. It suppresses accidental opening after a long press and supports listener disposal.

Async image imports capture their team/map context before reading files and discard results when that context changes. Logo uploads also guard against a later selection or removal. Capture form values before awaiting IO rather than reading a potentially changed form afterward.

## Shared document and local persistence

Teams use one `team.consilium.json` document containing the full plan. Player profiles live in `plan.keeps`, alongside team settings and maps. Only the current team document format is supported.

The plan retains shared player records and team metadata outside map layouts. Named maps contain layout snapshots referencing player IDs. The active layout is projected into the plan fields consumed by the renderer and synchronized back after edits. Map snapshots store placement fields, not player names, account IDs, avatars, or future statistics.

`services/team-workspace.js` coordinates account and team operations using injected transports and a `persistence/team-repository.js` adapter. `services/team-files.js` coordinates folder/file authorization and loading without DOM access. It preserves Drive resource keys and reads team metadata directly from the document. `persistence/team-draft.js` decides whether to restore a dirty local draft and retains its original shared-file base revision.

`persistence/draft-queue.js` debounces edits and serializes every write, including shared-save acknowledgments. Each snapshot retains its account/folder/file key. Team navigation flushes pending writes; a failed flush is reported. IndexedDB opens lazily. Remembered-team shortcuts live separately in localStorage, and forgetting a shortcut does not delete the shared folder or draft.

## Synchronization

`services/project-sync.js` owns the saved snapshot, dirty state, remote-change detection, and save/reload coordination. `services/player-cache-sync.js` owns roster-wide automatic cache-refresh passes, with an independent resettable lifetime and guards for editing, dirty state, permissions, and remote changes. A pass collects profiles against one immutable team snapshot, validates them, commits them together, and saves the team once. Local edits, navigation to a different map snapshot, permission changes, or workspace resets invalidate the batch. Individual unavailable files are skipped and reported. `ui/save-controls.js` presents that state. Metadata is checked every 30 seconds while the planner is visible and on window focus. Clean local state plus changed remote content shows Reload; local edits keep the Save/conflict workflow.

Checks and saves capture a generation belonging to the current team. Results from an earlier team or sign-in session cannot update the new team's state. A revision change with identical shared content advances the tracked revision and draft base without displaying a teammate-change warning. Save retries one revision conflict only when a fresh download still matches the saved snapshot. Edits made during an upload remain dirty afterward.

Drive's version preflight is not an atomic compare-and-swap. The application detects observed conflicts, but simultaneous uploads can still race. Tokens remain in memory. Public deployment configuration lives in `web/google-config.js`; secrets do not belong in browser modules.

## Player statistics

`domain/player-details.js` implements profile-only detail edits. `domain/player-details-schema.js` validates the optional `player.details` record through focused validators. `domain/troops.js` defines canonical troop order, labels, buff contexts, and troop totals; `domain/attack-marches.js` owns march construction, validation, and totals. `ui/player-details.js` composes the tabbed editor from `player-buffs.js`, `player-march-sizes.js`, and `player-marches.js`; `ui/player-screen.js` commits identity and details as one edit. Buffs use independent city/rally/solo contexts; march sizes are entered per troop type at the fixed +200% boost (no conversion is applied). Named attack marches contain explicit tier counts plus per-type base counts and an inclusive `baseThrough` tier. Totals multiply each base count by that tier range, and validation rejects overlapping explicit tiers. Legacy per-player subcity records remain preserved. The team-level Subcities tab uses a separate `plan.subcities` registry with fixed server coordinates, independent of formation layouts. `domain/subcities.js` validates culture, color, coordinates, and specific named red city references; `ui/subcities-screen.js` owns the card grid, `ui/subcity-dialog.js` owns the form draft and permission/context checks, and `ui/subcity-browser.js` owns the visual castle chooser and its filters. Each registry record has an optional `ownerId` referring to a team player. This is the only ownership record; the player Subcities tab derives its list from those references. Ownership mutations require team write access, do not modify the standalone player profile, and removing a player clears references without deleting cities. `ui/player-subcities.js` handles assignment/unlinking and `ui/subcity-card.js` shares card presentation across both screens and the assignment chooser. Team permissions gate edits. Generated `catalog.subcityTypes` records and `assets/subcities/` images come from `consilium_assets.subcity_catalog` (pure rules) and `consilium_assets.subcities` (image extraction) during asset acquisition; no downloaded catalog or artwork is checked in. `domain/march-generation.js` owns strategy weights, capacity inheritance, validation, support-layer reservation, and integer allocation. Marches can override the player's per-type capacity using `capacityOverride`; null follows the player's default. A `generation` record stores strategy, highest tier, support-layer size, percentages, and a whole-march `manual` flag. Editing any count or base layer sets that flag and freezes all troop counts; capacity changes still affect the available/overflow display. Reset to strategy explicitly clears it. Existing saved counts without generation metadata are treated as manual when opened. Generation writes all four troop types at every explicit tier, including supporting types hidden from the main count column, plus T1–T9 base layers. `editPlayerDetails` regenerates automatic marches when defaults change, including changes outside the UI. `application/march-draft.js` owns uncommitted marches, edits, generation errors, and preset persistence. Inputs update that model directly, and returned snapshots do not alias its mutable draft. `ui/player-march-settings.js` renders capacity and strategy controls. Ground/Mounted start at 30/50/20 across the highest three tiers; Archers retain the workbook's T12–T15 allocation, and big/small Siege retain their fixed-tier emphasis. Above T15, Archer/large Siege defaults retain the workbook allocations and give T16/T17 support counts until percentages are adjusted. Lower-tier allocations are normalized to 100%. The march editor offers T16 by default at K45 and T17 at K50, with a per-march highest-tier override. Blank numeric values are null rather than zero.

Profiles remain cached in the shared plan outside map snapshots. New roster entries also receive central player files; existing embedded profiles receive one when an administrator unlocks them. Team edits retain normal Undo, drafts, and Drive saves. Empty UI presets are not inserted into a profile until data is entered. The editor keeps uncommitted detail inputs when unrelated profile appearance changes render the same player.

## Adding further player statistics

Start with domain fields and validation for one feature at a time: buffs, march size, troop composition, or subordinate cities. Define units and limits explicitly. Keep derived calculations in pure domain functions rather than storing duplicate totals.

Add a focused profile command and profile-page section for each feature. Commands should preserve unrelated profile data and all map placements. Use the TeamStore commit path so Save, draft recovery, and Undo apply consistently. A stat change should not alter map layout snapshots or require the placement inspector to know the stat schema.

Player records remain embedded in the team document, with optional `playerSource` metadata containing a central Drive file ID, revision, last synchronization time, and profile baseline. `domain/player-document.js` strips roster identity and placement fields from standalone profiles, validates linked documents, and merges independent changes against that baseline. Arrays such as marches are atomic conflict units. Import validation also checks source metadata.

`services/player-files.js` owns per-account source-file grants and downloaded profiles. `TeamRepository` remembers which files an account unlocked; each new workspace verifies remembered access. The team contains no authorization flags. The roster renders from cached team profiles. Opening a profile probes that source’s metadata; returning to the app rechecks the active profile. Read-only source content is not downloaded just for this probe. A writable, app-accessible source can be loaded without Picker; denied probes remain silent and leave the unlock fallback available. Native Google Drive sharing provides permissions; Picker unlocks authorize those existing files for the app. Team-file write access enables roster/map administration but does not unlock player editing. New files must be created in the central team folder, with no fallback to personal storage.

`services/player-profiles.js` coordinates adding and unlocking players, authoritative source saves, editor overlays, and validated cache transactions. It receives plan reads, validation, and commits through explicit callbacks. `ui/player-workflow.js` composes views and presents results; it does not inspect transport state or coordinate cache writes. `services/player-files.js` keeps downloaded profiles in a private map and exposes snapshots and access checks. Workspace composition injects player-change and editing callbacks rather than attaching them after construction.

All unlocked profile edits write directly to the authoritative standalone player file, regardless of team permissions, using a separate account/file-scoped IndexedDB draft. Team editors also update their local team cache after a successful profile save. Admin sessions automatically pull accessible player files across the roster and save refreshed caches on team entry, focus, and the 30-second check. Cache refresh never uploads profile values to a source or asks for a team/source merge. It validates profiles and preserves roster IDs and placement fields. Unchanged revisions and profiles do not create edits. Automatic cache saves pause for unsaved team edits, remote team changes, or an active save. Player files lacking app authorization remain cached until access is granted. Concurrent profile saves still use revision checks and three-way merging of stale editor fields, with a choice only for overlapping source edits. Every source operation checks its workspace generation so an outgoing team's operation cannot update a new team's UI. These are independent Drive writes rather than an atomic transaction across documents.

Test validation boundaries and preservation across profile edits, map switches, Undo, and shared-file round trips. Add browser scenarios alongside `tests/browser/players.js` and `player-appearance.js`, rather than expanding the map-gesture scenarios.

## Resources and terrain

`services/resources.js` loads catalogs and terrain independently. `services/terrain-loader.js` reads the extracted manifest and binary grids; `domain/terrain.js` provides a `TerrainCatalog` per resource load and pure placement checks that receive terrain explicitly. Catalogs are independent, and resource data stays outside team documents. Blank maps bypass terrain restrictions.

`rendering/map-renderer.js` coordinates camera projection, drawing passes, and hit testing. `terrain-painter.js` owns terrain and moat passes, `entity-painter.js` owns sprites and highlights, and `image-cache.js` owns image loading. The renderer reports zoom through a callback and does not write screen content. Fixed-landmark identity is explicit rather than inferred from an ID prefix. The renderer uses original nearby tile sprites and a simplified distant overview. Server landmarks are rendered separately from editable entities and excluded from serialized layouts. Minimum landmark display scale makes the throne and temples easier to locate when zoomed out without changing their coordinates or collision footprints.

Catalog and terrain generation belong in `scripts/`, with generated resources in `web/assets/`. The commands are thin wrappers around the installable `consilium_assets` package under `src/`. `consilium_assets/castles.py` coordinates extraction; `prefab_reader.py` resolves Unity trees, `spine.py` reads atlases and runs the adapter, and `raster.py` composites textured geometry. Client configuration rules live in `catalog.py`, `prefab_catalog.py`, and `legacy_catalog.py`. Runtime application code does not use the offline Spine renderer.

## Verification and formatting

Run `npm run format:check`, `npm test`, `npm run test:browser`, and `npm run build`. `npm run format` formats maintained JavaScript, CSS, HTML, and documentation while excluding generated assets and private configuration.

Unit tests cover domain commands, state ownership, layout preservation, local writes/recovery, Drive operations, and synchronization. `tests/architecture.test.js` checks module boundaries and import safety. The browser runner composes focused scenarios under `tests/browser/`, exercises mocked Google services, and checks responsive layout and runtime resource errors. Screenshots are written to ignored `test-results/`.

Mocked browser checks do not replace testing live Google authorization on a configured deployment. The Pages workflow installs locked dependencies, checks formatting, runs unit tests, and builds before deployment.

## Navigation, migrations, and shared controls

`ui/navigation.js` stores team, screen, player, and map IDs in the URL fragment and applies browser history without recording data edits. Initial links open after sign-in and still pass through ordinary Drive authorization. Invalid player IDs fall back to the roster. Team opening suppresses route writes until the workspace has adopted the new document.

`domain/document-migrations.js` normalizes historical version-1 records before validation and rejects unsupported plan versions. Envelope parsing is separate from plan validation.

`ui/choice-control.js` shares selected portrait/caption controls, their permission state, and optional removal gestures. Subcity castle and owner choices use it, including owner locking during player-context creation. `ui/portrait.js` shares portrait content across pickers and roster cards. Controller-owned subcity buttons are excluded from the generic read-only observer so their mode restrictions cannot be overwritten.

Browser checks cover dashboard counts, URL navigation, subcity filters and locating, and clipping at phone and intermediate viewport widths. Both pull-request verification and Pages deployment run those checks against the built site.

## Rally-centered arrangement

`domain/rally.js` selects the highest-level keep by default and retains explicit choices per map through `rallyManual`. `domain/formation.js` uses one compact integer-tile search, centers on the placed rally setter, and ignores historical spacing/layout controls. Unplaced rally setters start at the map midpoint or its nearest free position; existing placed rally setters never move during Arrange. `ui/formation-controls.js` exposes Arrange in the map toolbar. `ui/formation-list.js` exposes hover/long-press stars; the map canvas only handles placement and navigation. Catalog castle/building dimensions are read-only in the placement inspector; blocked tiles retain adjustable sizes.
